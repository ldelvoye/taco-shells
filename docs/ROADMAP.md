# Features

- Settings tab: `cmd+,` opens a tab with a control for every setting (theme, font and size, cursor, scrollback, restore on launch) instead of opening `settings.json` in `$EDITOR` in a new terminal. The file stays the source of truth: a change in the tab is written back to it and applies live, the same as a hand edit, so the write has to keep the comments and formatting the user put in the file. Keybindings can follow as a second section once settings work.
- Terminals on a remote dev machine: look into what it would take for a row to hold a session running on a cloud dev machine instead of this Mac, with the same agent state as a local row, and for that session to keep running while the laptop sleeps or the app is quit. This is an investigation before it is a build: find out what such a machine's own CLI already offers for starting, listing and attaching to sessions, and whether the app should drive that CLI or only show what it reports.
- Which agent a terminal is running, at a glance. Once a second agent is supported and people run two side by side, a row should show whether it holds Claude Code, Codex or another agent, for instance an icon per agent beside the session marker. Grouping terminals by agent automatically could build on the same thing. Waits for a second harness: Claude Code is the only one today, so there is nothing to tell apart.

# Distribution

- Release page at `tacoshells.dev`: a page whose job is to get someone who has never heard of Taco Shells to a working install. It leads with what the app does and the install command from the README in a box with a copy button, and has no download button: a build downloaded in a browser reports as damaged. The page can serve `install.sh` at its own address or redirect to the copy on GitHub's `/releases/latest`. The domain is not bought yet; it was open on Namecheap on 2026-11-23. Still to decide: where the page's source lives and where it is hosted.

# Architecture

- How many terminals one window can hold, measured. Every terminal is a live xterm in the single renderer process for as long as its shell runs: a WebGL context from the first time it is shown, up to 100,000 lines of scrollback, and its output arriving over IPC on the same thread that draws the sidebar. Chromium caps how many WebGL contexts a page may hold, and a terminal that loses its context drops to xterm's slower DOM renderer and stays there. Find where this starts to show (typing lag, memory, lost contexts) by opening far more terminals than anyone does today, several of them printing at once, before choosing a fix. The small fixes stay inside the renderer, such as a hidden terminal giving its context back. The large one is a core that owns the shells, their scrollback and the workspace model with no window attached, and a UI that only draws what the core reports. The remote dev machine item under Features asks for some of the same separation, so read the two together.
