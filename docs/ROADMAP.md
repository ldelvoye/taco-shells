# Look and settings

Three pieces of work, done in this order, each one building on the one before. They share a reason: a Windows port is wanted soon, and the Mac conventions the app leans on today will not look right there.

- Visual identity: give the app a look of its own that holds up on both macOS and Windows. Today the window's colors are VS Code's Dark+ and Light+ copied over, the accent is VS Code's blue and the font is Apple's system font. The Mac-only parts of the look are that font, the title bar laid out around the traffic lights and the styling of the right-click popups. The only things that belong to Taco Shells are the icon and the wordmark, and the icon's colors appear nowhere in the window. The outcome is a set of decisions (colors for both themes, type, and the shape of rows, popups, buttons, banners and fields) applied to the window as it stands. Still to decide: what it looks like, how much of the icon's character comes into the window, and whether the terminal's own colors are part of it.
- The menu bar's jobs move into the window: everything the app can do is reachable from the window itself, so nothing depends on the macOS menu bar. Today the menu bar is the only way to reach an agent's setup (Set Up, Remove Setup, Switch to Managed Setup, Show Hook Scripts in Finder), Restart to Update, About and the developer tools. Comes after the identity, which says what a control in the window looks like. Still to decide: where each of these goes, and what is left in the macOS menu bar afterwards.
- Settings page: `cmd+,` opens a page with a control for every setting (theme, font and size, cursor, scrollback, restore on launch) instead of opening `settings.json` in `$EDITOR` in a new terminal. It is built in the new identity and reached from the window, not from the menu bar. The file stays the source of truth: a change on the page is written back to it and applies live, the same as a hand edit, so the write has to keep the comments and formatting the user put in the file. Keybindings can follow as a second section once settings work. Still to decide: whether the page is a tab in the main window or a window of its own.

# Features

- Terminals on a remote dev machine: look into what it would take for a row to hold a session running on a cloud dev machine instead of this Mac, with the same agent state as a local row, and for that session to keep running while the laptop sleeps or the app is quit. This is an investigation before it is a build: find out what such a machine's own CLI already offers for starting, listing and attaching to sessions, and whether the app should drive that CLI or only show what it reports.
- Which agent a terminal is running, at a glance. Once a second agent is supported and people run two side by side, a row should show whether it holds Claude Code, Codex or another agent, for instance an icon per agent beside the session marker. Grouping terminals by agent automatically could build on the same thing. Waits for a second harness: Claude Code is the only one today, so there is nothing to tell apart.
- What agents can do with the agent activity panel: a spike, once the redesign of the window (the look and settings work above) is built. The redesign puts a panel beside each terminal that logs what its agent was asked, did and changed, and gives the agent a place to share things with you, such as a diagram, a note or a plan. That needs a channel from the agent to the window, and the channel may let agents do things they could not do before. Find out what comes naturally from it on the backend before choosing anything to build.

# Distribution

- Release page at `tacoshells.dev`: a page whose job is to get someone who has never heard of Taco Shells to a working install. It leads with what the app does and the install command from the README in a box with a copy button, and has no download button: a build downloaded in a browser reports as damaged. The page can serve `install.sh` at its own address or redirect to the copy on GitHub's `/releases/latest`. The domain is not bought yet; it was open on Namecheap on 2026-11-23. Still to decide: where the page's source lives and where it is hosted.

# Architecture

- A terminal engine that brings a terminal back whole and at once. The shells, their screens and the arrangement now live outside the window, which keeps a view only for the terminals on screen and the eight shown most recently (`AGENTS.md`, "The three contracts"; the measurements are in `scripts/measure/README.md`). What is left is the engine on both sides, xterm.js. Bringing back a terminal with a full 100,000-line scrollback takes over half a second, during which the other terminals get no output, because xterm can only write a whole buffer out and read it back in. Its snapshot also drops the scroll region, the saved cursor, the cursor's shape, tab stops, the line-drawing characters and hyperlinks. An engine whose snapshot keeps all of that, and which sends the visible screen first and the history after, removes both. Ghostty's library does, measured in a spike; what it lacks is a view for the window, which would have to be written. `src/conformance/` is the test a new engine has to pass, and its expected failures are the list of what xterm loses.
- The core in Rust. The terminal runtime and the workspace are TypeScript, in a process of their own and in the main process. They talk to each other and to the window only through the plain-data messages in `src/protocol/`, so either can be rewritten behind those messages without the other parts changing.
