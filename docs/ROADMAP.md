# Look and settings

Three pieces of work, done in this order, each one building on the one before. They share a reason: a Windows port is wanted soon, and the Mac conventions the app leans on today will not look right there.

- Visual identity: give the app a look of its own that holds up on both macOS and Windows. Today the window's colors are VS Code's Dark+ and Light+ copied over, the accent is VS Code's blue and the font is Apple's system font. The Mac-only parts of the look are that font, the title bar laid out around the traffic lights and the styling of the right-click popups. The only things that belong to Taco Shells are the icon and the wordmark, and the icon's colors appear nowhere in the window. The outcome is a set of decisions (colors for both themes, type, and the shape of rows, popups, buttons, banners and fields) applied to the window as it stands. Still to decide: what it looks like, how much of the icon's character comes into the window, and whether the terminal's own colors are part of it.
- The menu bar's jobs move into the window: everything the app can do is reachable from the window itself, so nothing depends on the macOS menu bar. Today the menu bar is the only way to reach an agent's setup (Set Up, Remove Setup, Switch to Managed Setup, Show Hook Scripts in Finder), Restart to Update, About and the developer tools. Comes after the identity, which says what a control in the window looks like. Still to decide: where each of these goes, and what is left in the macOS menu bar afterwards.
- Settings page: `cmd+,` opens a page with a control for every setting (theme, font and size, cursor, scrollback, restore on launch) instead of opening `settings.json` in `$EDITOR` in a new terminal. It is built in the new identity and reached from the window, not from the menu bar. The file stays the source of truth: a change on the page is written back to it and applies live, the same as a hand edit, so the write has to keep the comments and formatting the user put in the file. Keybindings can follow as a second section once settings work. Still to decide: whether the page is a tab in the main window or a window of its own.
- What a plain shell's row is called becomes a setting. Today a row with no agent shows the name of the folder its shell is in ("~" at home), where the Electron app showed the shell's own title (user, machine and folder). The setting would offer other names, such as the short path or the running program, and which ones is still to decide. It belongs on the settings page.

# Features

- Terminals on a remote dev machine: look into what it would take for a row to hold a session running on a cloud dev machine instead of this Mac, with the same agent state as a local row, and for that session to keep running while the laptop sleeps or the app is quit. This is an investigation before it is a build: find out what such a machine's own CLI already offers for starting, listing and attaching to sessions, and whether the app should drive that CLI or only show what it reports.
- Which agent a terminal is running, at a glance. Once a second agent is supported and people run two side by side, a row should show whether it holds Claude Code, Codex or another agent, for instance an icon per agent beside the session marker. Grouping terminals by agent automatically could build on the same thing. Waits for a second harness: Claude Code is the only one today, so there is nothing to tell apart.
- What agents can do with the agent activity panel: a spike, once the redesign of the window (the look and settings work above) is built. The redesign puts a panel beside each terminal that logs what its agent was asked, did and changed, and gives the agent a place to share things with you, such as a diagram, a note or a plan. That needs a channel from the agent to the window, and the channel may let agents do things they could not do before. Find out what comes naturally from it on the backend before choosing anything to build.
- The agent activity panel's Shared section as a menu: a place where you see the important things your agents have shared at a glance, instead of reading down a list. Today Shared is a plain list of what an agent gave you. Turning it into a menu needs design of its own before anything is built. Still to decide: what makes a shared item important, how items from several agents sit together, and what opening one does.
- A subagent's report reads as its own entry in Agent Activity. Today, when a subagent hands its report back to the agent that started it, the log shows it under "You asked", with the whole frame Claude Code wraps around the report (the `<agent-message>` tags and the paragraph saying the text is model output). It should show as a message from the subagent, with only the report.
- Subagents mapped out in Agent Activity: see which subagents an agent started, what each was asked, whether it is still running, and what it handed back, instead of finding their steps mixed into one log. This may mean redoing what the panel holds, since it was laid out for one agent's notes and steps and now also carries Shared, messages between sessions and subagents. Needs design of its own before anything is built. Still to decide: how a subagent's work sits beside its parent's, how far down nested subagents are shown, and what happens to the log as it reads today.
- Agents that drive the app: the MCP server that gives an agent its activity tools could later also let it work with terminals the way the user does: open one in a folder with an agent and a first message, name it, move it, put it in a tab group, close it, and read the state of the others. An agent orchestrating a piece of work could then start real sessions itself and keep them organized, instead of the user opening each one by hand. The server starts with the activity tools only. This waits on things the app cannot do yet: it cannot name a row, and it cannot tell a caller which terminal it just opened. Still to decide: how a terminal the user is working in is kept apart from one an agent opened, and how many terminals an agent may open.

# Distribution

- Release page at `tacoshells.dev`: a page whose job is to get someone who has never heard of Taco Shells to a working install. It leads with what the app does and the install command from the README in a box with a copy button, and has no download button: a build downloaded in a browser reports as damaged. The page can serve `install.sh` at its own address or redirect to the copy on GitHub's `/releases/latest`. The domain is not bought yet; it was open on Namecheap on 2026-11-23. Still to decide: where the page's source lives and where it is hosted.

# Architecture

- Bringing a terminal back whole and at once, which needs another terminal engine. The shells, their screens and the arrangement now live outside the window, which keeps a view for the terminals on screen and for the most recently shown others until there are eight (`AGENTS.md`, "The three contracts"; the measurements are in `scripts/measure/README.md`). A terminal with no view is brought back from a snapshot, and with xterm.js on both sides that snapshot is the whole buffer written out and read back in: over half a second for a full 100,000-line scrollback at the 95th percentile, in one call during which the runtime does nothing else. The snapshot also drops the scroll region, origin mode, the saved cursor, tab stops, the line-drawing characters, the cursor's shape and hyperlinks. An engine whose snapshot keeps all of that, and which sends the visible screen first and the history after, removes both problems. Ghostty's library is the candidate, since its snapshot is built that way; it has no view for a window, which would have to be written, and it has not been tried in this app. `src/conformance/` is the test a new engine has to pass. Five of the losses above are expected failures there and turn green when an engine keeps them; the cursor's shape and hyperlinks have no case yet.
- The core in Rust, later. The terminal runtime, in a process of its own, and the workspace, in the main process, are TypeScript. The order was decided when the split was designed: take the core out of the window first, in TypeScript, and rewrite it afterwards. Each talks to the other and to the window only through the plain-data messages in `src/protocol/`, so either can be rewritten behind those messages without the other parts changing. The remote dev machine item under Features leans on the same separation, so read the two together.
